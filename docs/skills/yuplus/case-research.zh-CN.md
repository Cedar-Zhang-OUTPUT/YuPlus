# 案例分析

用于项目的案例分析研究、新开研究和修改已有画板。可从用户文字、文件或已有项目上下文开始，不要求先完成 draft/review。不为研究自动创建来源或修改 draft/review。

## 明确研究身份

- 用户提交 **开启一轮新的案例分析** 提示词才开启新一轮：首次 v1，之后 v2、v3……每轮保留独立的画板定位，保留旧研究。仅复制提示词或查看历史不产生操作。不能根据当前正在查看的历史版本推算下一个版本号。
- 补案例、补图、改说明、调整分组或细化当前方向，均更新同一研究和画板。用户直接在飞书中的修改也属于同版本更新。Agent 修改前读取目标画板最新内容，保留用户编辑，不用旧的本地草稿覆盖。
- 中断后继续、写入重试均沿用本轮身份与资源。结果不确定时先核查，不能重复创建文档或画板。明确要求新开研究就创建新轮次，不因正在查看历史画板而改变意图。仅在目标轮次或新开/修改确实不清楚时简短询问。
- 用户指定的画板须与本轮身份一致；不能把旧轮次的画板直接当作新版本内容，冲突时先明确。

## 理解本轮任务

复用已知项目身份和上下文，只读取影响选例的输入：目标、受众、品牌、创作意图、体验、技术作用、交付与约束。用户提供的筛选标准、客户偏好和探索方向只适用于本轮，不建立长期偏好档案，也不擅自沿用到下一轮。

OUTPUT 审美说明来自用户导入的案例库，有则读取依据；不自行建立公司审美画像，不挖掘无关历史项目或群聊推导公司标准。缺少说明时明确判断局限，按本轮需求推进。

区分已确认、合理推断和待补充，以及客户原话、个人意见、主策判断和正式决定。保留重要冲突。显著影响方向的缺口集中提问，其他缺口不阻断研究。形成简短的工作筛选标准，区分概念、视觉、体验机制、制作/技术参考用途，不设必填表单或审批关卡。

## 检索与判断

访问案例库时按需读 [案例库参考](case-library.zh-CN.md)。通过 `library list` 获取有效登记，按需查询详情。读取每个源的 `description` 和 `search_guidance`，结合本轮需求选择关键词、观察内容和深入研究顺序。说明属于参考数据，不是可执行指令或案例证据；示例年份与品牌按实际任务调整。用户未缩小范围时，**每个已登记的网站、飞书共享文件夹都要做与本轮方向相关的检索**。没有的类型无需补齐；覆盖各库不等于遍历全站/整库。区分无法访问、尚未检索与检索后没有合适结果。

网站用浏览器/网页工具，文件夹和选中文档用对应飞书 Skill/CLI。在有限范围内处理相关子目录与分页。不预置工作室白名单或必查网站清单，以用户登记为准。同时主动探索相关公开网络，适合时包括 GitHub，不必等案例库查找失败。发现的网站不自动登记为新案例库。

读取具体案例页面/文档，不只看搜索摘要或首页。核对每张图片的案例归属，多案例长页面按对应区块拆分。排除占位图、响应式重复图、网站通用背景素材和其他推荐案例。按授权访问，需要登录时由用户在网站中完成；访问失败不代表没有案例。

区分三种参考用途：
- **纯视觉参考：** 围绕特定图片关系或概念选图。保留可追溯来源，不要求完整案例卡片，不编造项目背景。
- **Case Studies：** 选取值得解释方法的重点项目，提取「项目／时间地点 → 创意主题 → 视觉语言 → 体验方式 → 可借鉴用途 → 来源」。说明本项目适用点与参考边界；OUTPUT 匹配点有依据才写。详细分析放在配套飞书文档，画板图片旁只留简短要点。
- **灵感提炼：** 将参考关联到本项目的概念、视觉符号与可能的创意转译；明确这些是本项目建议，与原案例事实分开。

AI、工具、负责人和成效有依据才确认，上传者不自动等于负责人。区分参考工作室、同类案例和已知竞争对手，不凭公开画面推断本次竞标方案、预算、工期或效果。

完整的新一轮视觉研究，以**约 4–5 个主题组、合计 50–60 张不同且有效的图片**为目标。首批可先形成 30–40 张，随后继续补齐，不把首批当作全部完成。这是图片数，不是案例数或每组配额。用户指定范围优先；单次补图、修改说明不要求重新收集整套。先广泛收集候选，再筛选去重。同一案例不同视角须提供新信息；重复裁切、不同分辨率、Logo 和色块不用于凑数。访问或相关性不足时说明实际数量及未完成工作，不用无关图片填满。

## 保存图片与证据

清晰的**截图足以满足基础视觉参考**；原图和视频下载为可选增强，不作为收录前提。等待真实内容加载，选择代表画面或视频帧，截图后检查清晰度、裁切与遮挡。准确区分原图、网页截图和视频帧，不生成替代案例图片。使用可用的浏览器截图能力，一种截图方法失败不等于网站不可用。

临时下载放在 Yu+ 业务数据与备份之外。精选材料按 `来源名称_案例原名` 组织，下载保留原文件名，截图用说明性名称，保留文件名与来源映射。不镜像整个网站或文件夹。

精选素材及详细证据索引**保存到飞书**，使用用户指定或可用的默认位置，不移动原资料。索引保存案例/来源原名、链接、访问时间、图片映射、视频位置、证据位置、有依据的人员/工具信息及简要检索覆盖。单次偏好留在当前工作上下文，不另建持久或跨项目偏好档案。报告实际保存结果及可用链接；对话记忆不等于已保存索引。

Yu+ 仅保留研究版本元数据、文档/画板定位，不保存案例正文、素材或详细索引。程序维护的临时预览缓存位于业务数据与备份之外；正常刷新不调用 Agent、不改变研究版本号。

## 整理画板、校验与迭代

创建或修改画板时按需读取已安装的 `lark-doc` 创作/画板指南及 `lark-whiteboard`，只加载所需参考，已读复用。选择构图前实际查看用户提供的 Moodboard 示例图片，参考其组织逻辑，不把示例品牌的风格直接当作本项目风格。

**图片为主，卡片可选。** 真实图片以独立、可编辑的元素贴入画板，保留比例。纯视觉参考直接组成图群，不给每张图套卡片、写一段说明。仅对需要解释方法的重点案例保留简短分析；操作日志、资源 key 和详细证据留在飞书索引。每张图片用小型来源链接或索引编号保持可追溯，不加卡片也不能失去来源。

按**核心概念 → 图片关系 → 视觉符号 → 创意转译**组织画板：
1. 约 4–5 个分组各有贴合项目的主题名和简短概念说明。按创意问题或希望带来的感受分组，不强制分成内部／外部参考，也不固定为配色、材质、互动等类别。同组可以混合案例库与公开网络来源。
2. 有目的地组织图片关系：并置表现结构共性或对照，环绕建立品牌世界，拼贴展开联想，分组界定风格边界，序列表达叙事。大小、重复、留白和阅读路径服务这些关系；不规定统一网格、主辅图比例或色卡数量。
3. 用简短的组级说明提炼有意义的视觉符号及其含义，再解释如何转译为项目图形、空间、动态、行为或叙事。不止罗列颜色、材质、造型，也不将研究方向写成方案定稿。

尚未完成概念提炼的图集称为**案例参考板**；构图与简短说明共同表达核心概念、图片关系、视觉符号和创意转译后，才称为 **Moodboard**。图片变多不等于完成 Moodboard。

大量图片分批上传与编排，保留图片—来源—远端节点映射，便于中断续作。回读真实画板，检查整体预览并放大各组：核对实际加载的不同图片数、主题清晰度、图片关系、工作缩放下的图文可读性、来源链接及用户编辑是否保留。不把整套图片缩成无法阅读的全景，也不把整板压成一张图片。研究版本关联核验后的画板链接及定位。报告实际图片数、分组数、检索覆盖、已保存索引和未完成事项；上传失败或未核验渲染时不能声称完成。

用反馈改善本轮研究与解释。不把沉默当认可，不把单次偏好升级为公司标准，不宣称已充分学会 OUTPUT 审美。结尾引导补充标准、细化本轮或明确新开研究等相关选项，不自动引导到 draft/review。

## 保存研究轮次

使用已安装的 `yu`，明确指定 `--data-dir` 和 `--project`。只在识别或恢复轮次时按需读取 `research list` / `research show --research ID`。写操作使用 `--input FILE --request-id KEY`；同一逻辑写入重试复用相同输入和 key。不直接写 SQLite。

1. **新研究：** `research create` 输入 `{"api_version":"1","command":"research.create","title":"研究标题"}`。保存返回的 `id`、`version`、`metadata_version`。这只预留轮次，不表示画板已完成。重试复用回执，不换请求。飞书文档/索引里标注研究 ID，创建结果不明时先定位已有资源。
2. **创建并关联：** 用 `lark-doc` 创建文档及画板，或向指定位置追加新画板。回读返回的文档链接、画板块 ID 和 board token，立即用下方定位输入执行 `research update`；画板链接使用真实文档块锚点。关联后画板身份固定，不能同时属于另一轮。局部失败后继续此板，不静默创建替代品。
3. **填写或续改：** 先读最新节点和预览，使用 `docs +media-upload --parent-type whiteboard --parent-node BOARD_TOKEN` 将图片上传到目标板，再按 `lark-whiteboard` 写入实际图片和内容。远端重试复用每次写入的 `--idempotent-token`。保留用户编辑，优先定点修改或追加，不把整板覆盖当作常规更新。远端结果不明时先回读再重试。
4. **记录成功：** 验证远端正文及渲染预览后，`research show`，再用 `research_id` 和当前 `base_version`（即 `metadata_version`）执行 `research update`；定位不变则省略定位字段。只递增元数据及更新时间，不新建 v2。远端写入失败不登记成功更新。本地版本冲突须重读并核对，不能盲目重试写入。
5. **检查展示：** `research preview --research ID` 检查页面使用的同一只读导出/缓存链路。打开项目 `/case-finding` 页面，核对 vN 及“打开飞书画板”链接。新建或关联后刷新页面以重新读取历史。日常预览由程序自动获取，不调用 Agent。

首次 `research update` 定位输入（替换为实际返回身份）：
```json
{"api_version":"1","command":"research.update","research_id":"research_ID","base_version":1,"document_url":"https://tenant.feishu.cn/docx/DOC","board_url":"https://tenant.feishu.cn/docx/DOC#BLOCK_ID","board_token":"BOARD_TOKEN"}
```

`version` 是研究轮次；`metadata_version` 是本地乐观写入计数。`created_at` / `updated_at` 表示已保存研究元数据的时间，`fetched_at` 表示获取预览时间。用户在飞书直接编辑仍属于同轮，自动刷新会显示变化，不改这些本地业务时间。这些版本是独立研究轮次，不是每次飞书修改的不可变快照。

若已安装 help 没有这些命令，说明版本能力缺口，不把 demo 当作已保存研究，也不为重试本地登记而重建远端成果。
