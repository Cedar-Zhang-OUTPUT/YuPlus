# 从群聊中形成有用的项目信源

对应英文 `references/chat-materials.md`。解释群聊批次、选择信源或处理其中附件时按需读取。讨论边界由 Agent 理解，CLI 负责保存证据与回执，不代替语义判断。

## 先理解一段对话，再判断其含义

监控消息队列是操作历史，不等于用户的原始材料库。拉取全部可访问历史，不代表逐条 capture，也不代表一条消息生成一个 draft 子目。

结合相邻发言、参与者、回复、日期和关联材料，围绕同一业务问题或决策过程划分讨论片段：提议、澄清、分歧与回应需要放在一起理解。时间间隔和分页边界本身不是话题边界。不同议题、前后两次决定要区分，不能把后来的反转压成早先已达成的共识。“是的”“最新版”、@人或图片占位符，必须先找到所指内容。只有本身完整、权威与适用范围明确的独立发言，才适合作为单条片段。

25 条批次截断讨论时，可将 `pending limit` 提高到 100，先补足上下文再处置。当前 CLI 只能暴露最早 100 条未处置消息；超过此范围的长讨论，用明确命名的有限续篇保留上下文和未定性，后续继续并在 draft 依据中关联。不能把一页消息说成完整决定，也不能为看到后续答案而丢弃中间信息。

系统通知、问候、普通确认、重复与无关闲聊通常只留在队列，以实际理由 `no_change`。不为取得回执制造信源、对象或决策。有上下文作用的确认放进对应片段，而非独立材料卡。“处理全部历史”指全部获得适当理解与处置，并非全部成为业务数据。

## 两种材料形态

**讨论片段：** 优先调用分组 `monitor capture`，传真实 `message_versions` 和可读的主题标题，例如“12月11日 · After Party 与晚宴形式确认”。保存为一份 `chat_segment` 信源，包含所选原始发言、发言人、时间与已核实的飞书定位。范围是这个片段，不是完整群历史。不要用 AI 总结替换原文；业务解读写入 draft。同一信源可以支撑多个业务子目，在依据 locator 中标明实际发言/参与者。决策保留决策者、时间、权限和条件；建议或疑问不能直接成为已采纳决定。原始技术标签可以保留在逐字信源里，不能进入业务简介。

**独立文件、文档、会议纪要：** 每份实际材料独立收录，和发送它的聊天区分。用相应飞书 Skill 取得原件或忠实导出物，实际读取，再通过 `assets[].storage="copy"` 复制到 Yu+ 文件池。file key、URL 或截图占位符只是取回内容的地址，不是内容。不能把地址粘入 Brief 就声称处理完附件。

- 群附件/图片：按 `lark-im` 的资源下载指引取得文件，再用 PDF、图片等合适工具读取；云盘文件使用 `lark-drive`。保留实际文件名、MIME 和原始字节。已下载群附件可用 `provider=local`、`resource_type=file/image`，provider key 按真实远端身份稳定构造，先查有无已有来源。技术身份只进元数据。
- 云文档/wiki：用 `lark-doc`，必要时结合 `lark-drive`，解析、读取和导出实际资源。保留飞书身份、规范链接、已知 revision，并在同一来源附上真实本地导出文件，不另外制造独立维护的“链接版”和“下载版”。只有完整 Markdown 可得时，保存忠实 `.md` 并标明 Markdown 采集，不伪称原生 PDF/DOCX。保留真实采集范围，局部片段不能冒充完整本地文档。
- 会议纪要：使用 `lark-meeting` 获取实际纪要/逐字稿/导出物，按返回类型读取。版本、会议发生时间与下载时间分开。
- 发送消息的真实 AppLink、消息身份放入文件资产 `locator` 或 draft 的 `source_refs[].locator`。讨论说明材料适用范围或采纳过程时，再引用讨论片段。只用已核实的消息/话题定位；只能打开群时标明群级定位，不编造精确消息链接。
- 同一文件反复发送复用来源；真正更新追加快照。旧方案与新版 Brief 保留版本和适用范围。“最新版”结合上下文理解，不能仅凭上传时间判断权威性。
- 无权限、下载失败、未读内容在对话/本轮总结中如实说明，保留已有链接和消息证据。不捏造正文，不把失败说成完成，不把 HTTP 错误、命令或访问日志写入对象。不可用材料可能影响解释时，保留未完成状态以便续办，不虚假标成已处理；用户明确允许不带此材料推进时可以如实记录，但不能声称读过。

## 对象写业务含义，不写聊天转储

每个子目表达一个连贯的业务事实、约束、问题或决定，使用真实对象字段。多条支持性发言合并为依据，不一条消息复制一条子目。材料是否归属客户 Brief/BD 同步，取决于实际内容的作用，不取决于是否有人在群里发过。

file_key、image_key、message_id、token、原始 `<file .../>` 标签、`[Image](img_...)` 占位符、下载路径、API 输出和同步日志，不写进 draft/review 的标题、描述、备注及业务简介；放在来源/资产元数据、依据 locator 和监控回执。业务上确有意义的版本名、交付文件名和逐字原始证据不在禁止之列。

例如“快闪日也有晚宴？”和负责人的“是的”，可以形成“活动形式：快闪日包含晚宴”，依据引用两句话所在片段。不要生成分别包含图片 key、问题和“是的”的三个“活动形式讨论”子目。`<file key="..." name="2026 Brief.pdf"/>` 应触发取回文件，只有读到的 PDF 正文才能支撑 Brief 要求。“最新版的 Brief”需要关联所指文件，不单独成为需求。

保存前检查：子目是否提供项目业务信息、依据能否支撑、用户能否打开底层材料。保存后回读受影响对象，发现技术标签或脱离上下文的回答就修正。仍然先改 draft 再改 review，保留版本历史。用户明确要求清理旧的噪声输出时，修改当前受影响子目和 review，保留旧版本；不删除原始来源/历史，不直接改 SQLite。本次能力不会自动清洗已收录项目。
