# Yu+ 对象关系与展示对照表

对象关系已确认 · v0.2 · 2026-10-13

依据：已读取的飞书《YU+ Dev》第 8 版，以及本轮产品讨论。本文用于确认对象关系和交互，不是完整数据库结构或实施计划。

## 1. 已确定的边界

- 一个本地应用管理多个独立项目；第一版由一名主策使用自己的 Codex 维护，其他人通过飞书提供材料和接收成果。
- 人在前端浏览，在 Codex 中表达修改和决定；Agent 使用外部技能读取材料，按 Yu+ Skill 处理，通过 Yu+ CLI 写入。
- 不做共识池；保留长期变更历史和决策记录，并在前端展示。
- 收集和整理是可往返的工作场景，没有必填项、信息齐全门槛或强制审核通关。
- 不展示材料的“读取中、部分读取、已处理”等 Agent 执行状态；保留有实际检查依据的“来源有更新”提示。
- review 是 Agent 基于 draft 编写的完整成果，必须保留来源和依赖，不能成为独立维护的另一套项目事实。
- **review 修改遵循硬性因果关系：先修改相关 draft 对象，再根据 draft 新版本重新生成或修订 review。不得直接修改 review 来绕过 draft。**

## 2. 关系总览

原始来源 → draft 项目对象 → review 完整成果

用户对 review 的意见 → 定位相关 draft 对象 → 修改 draft 并保留依据 → 更新所有受影响的 review 内容

| 层次 | 保存什么 | 如何变化 | 前端如何展示 |
|---|---|---|---|
| 原始来源 | 飞书来源与获取快照、本地原件、用户相关原话；保存可用的来源版本及定位信息 | 新材料或来源更新形成新记录/版本；不因 review 修改意见而改写旧原件 | 材料预览、打开原文、来源与版本、关联对象；飞书更新提示 |
| draft 项目对象 | 从来源提取的信息、用户补充、当前采用口径、判断、明确决定，以及必要的表达要求 | Agent 根据新材料或用户指示修改；区分事实、转述、推测和决定，保留历史 | 按对象类型展示字段、正文、材料集合；可查看依据、变化和被哪些成果引用 |
| review 完整成果 | Agent 组织的可独立阅读正文，以及段落/字段对应的 draft 对象和版本 | 只能以 draft 为依据生成或更新；保存旧成果和审核历史 | 连贯正文、来源跳转、关联 draft、版本差异和已有审核记录 |
| 变更与决策历史 | 谁提出了什么修改、依据、前后版本、影响对象；正式决定另外标识 | 追加记录；新决定可替代旧决定，但保留两者关系 | 项目活动历史；可筛选正式决策、按对象追溯 |

“原始来源”是统一保存机制，不取代业务中的“客户原始 Brief”“品牌资料”等名称。同一来源可以支撑多个 draft 对象；同一个 draft 对象也可以引用多个来源。

draft 与 review 的区分表示信息依赖关系，不要求用户按固定顺序填完各对象。

R01 的组织方式可以被 R04 复用，但 R04 必须保留到底层 draft 的依赖，不能只把 R01 当作一段无法追溯的新来源。任何新增判断或项目口径，先落实到 draft，再写入成果。

review 正文可以保存为版本化成果，用于阅读、对照和导出。它是有明确来源的派生成果，不是第二个项目事实编辑入口。飞书导出也应记录对应的成果版本；第一版不默认从导出文档自动反向改写本地成果。

## 5. “先因后果”的修改规则

### 5.1 用户从 review 提出意见

1. Agent 定位用户所指的成果段落/字段，读取其 draft 依赖。
2. 判断涉及哪些 draft 内容；如果现有依据不足，按必要程度询问，不能自行把推测写成用户决定。
3. 先修改相应 draft 对象，记录用户意见、来源及前后版本。用户意见不是客户原文，不能改写原始来源。
4. 查询这些 draft 内容影响的 review 段落和成果，而不只修改用户正在看的那一份。
5. 根据新 draft 生成或修订受影响内容，保存依赖版本和成果差异。
6. 如旧成果已有审核记录，保留旧记录，将实质变化涉及的部分标为待复核；不阻止用户继续其他工作。

“先修改 draft”是执行顺序，不等于每一步都要求用户确认。已有明确指示足以执行时，Agent 连续完成相关修改。

### 5.2 不允许绕过因果关系

- 不提供脱离 draft 依据的 review 任意正文覆盖入口。
- 保存 review 成果时必须携带所依据的 draft 对象、版本和对应关系；若依据在生成期间发生变化，不把结果作为基于最新内容的成果保存。
- 对用户要求的 review 修订，记录其对应的 draft 变更；只替换 review 文本、原对象保持旧值的操作不符合产品规则。
- 版本与关联检查可以由应用保证；内容是否忠实于依据仍需要 Agent 按 Skill 对照检查，不能声称数据库可以自动验证语义。

### 5.3 表达修改也先回到 draft

若用户只是要求“这段更简洁”“不要使用夸张措辞”，也不直接绕过 draft 修改成果。先在相关 draft 对象下保存面向该成果的表达要求，再据此重新组织文字。表达要求与事实字段分开，不为满足改写流程而捏造事实变化。

跨多个对象的表达要求可以作为 draft 层的成果编写要求统一记录并关联，不复制到每个对象，也不建立共识池。它属于内容编写依据，具体存储形式留待后续结构设计。

### 5.4 日期引用与语义改写

- 直接引用：日期、金额、规格等明确字段可从 draft 取值；已确认的历史成果/导出快照仍保留其当时版本，不悄悄改写历史。
- 语义依赖：背景判断、预算分配解释、创作者任务等由 Agent 理解变化后改写。
- 如果 draft 已修改但关联成果尚未更新，保留现有成果，并根据依赖版本差异提示“依据已变化”。这反映实际数据差异，不表示后端知道 Agent 正在做什么。
- 用户给出的一次决定应尽量由 Agent 在同次操作中落实到相关对象和成果；如果被中断，下一次可查询未更新的依赖关系接续处理。

## 6. 一个完整示例

用户正在阅读 R04 创作者 Brief，说：“这里不要要求创作者做成片，这轮只需要概念脚本。”

| 步骤 | 处理 | 用户可在前端看到什么 |
|---|---|---|
| 定位依据 | 找到 R04 交付段落对应 D18 的本轮交付条目 | 从该段落回看原交付要求及来源 |
| 先改 draft | 按用户指示将 D18 本轮交付从“成片”改为“概念脚本”，保存适用轮次和修改依据；原 Brief 文件不变 | D18 新值、旧值、修改理由；原材料仍可打开 |
| 检查影响 | 查到 R01 任务边界、R02 推进安排及 R04 交付段落引用该条目 | 相关对象与成果之间的关联 |
| 再改 review | 更新三处相关表达；如涉及日期/预算，不自行猜测新值，有依据才先改对应 draft 对象 | 三份成果中一致的交付内容及版本差异 |
| 保留历史 | 保存本次变更；如果属于明确的交付取舍决定，同时形成决策记录 | 项目历史中的决定、依据和影响范围 |

如果用户只针对某一位创作者调整要求，先在 D18 中建立或修改该创作者、本轮适用的交付条目，再更新相关成果，不能误改整个项目的通用交付要求。

## 7. 已确认的评审结论

1. 用户确认 23 类 draft 对象的业务归属和展示方式贴合主策工作，包括 D10 客户决策角色与 D20 内部职责的区分。
