# Yu+ 可视化界面信息展示 Spec

版本：v0.1，供需求审阅与 UI example 选择 · 2026-10-13

## 1. 用途与范围

这份 spec 定义用户在 Yu+ 可视化界面中需要看到的信息、需要辨别的含义，以及需要完成的查看动作。供选择 UI example 和后续视觉设计使用，不规定页面数量、导航位置、信息排布、组件形式、颜色、字体或交互动画。下文的“信息范围”不等于必须拆成独立页面。

使用者是一名在自己电脑上维护多个策展项目的主策。Codex 是对话、提供材料、提出修改和推进工作的主要入口；Yu+ 界面用于浏览 Agent 已保存的项目内容。其他人通过飞书提供材料和接收成果。

本稿以最新确认的场景定义、[对象关系](2026-10-13-yuplus-object-relations-design.md)及 [Yu+ Skill](../../../skills/yuplus/SKILL.md)为依据。完整业务属性见[对象参考](../../../skills/yuplus/references/objects.md)。此前[前端讨论稿](2026-10-13-yuplus-frontend-design.md)和演示原型不作为本次布局、视觉或对象数量的限制。

本稿中的“需展示”表示正式界面应支持查看该信息；不存在的业务数据不要求填满，也不必同时展开全部信息。第 10 节单独说明现有数据能力与待补能力，不将需求写成已上线功能。

## 2. 产品语义与浏览边界

只有两个工作场景：

| 场景 | Agent 的目标 | 用户需要看到什么 |
| --- | --- | --- |
| 信息收集 / draft | 收集当前任务需要的信息，整理到业务对象，维护来源和关联 | 已有哪些信息、来自哪里、各说法有什么不同、当前采用什么、还能补充什么 |
| 信息整理 / review | 根据已有 draft 对象组织和改写成所需成果，交给用户 review | 完整成果、段落依据、关联对象，以及反馈引起的变更 |

用户随时可以在 Codex 中补充材料或提出修改。Agent 更新来源和相关 draft，再更新受影响 review，交回用户查看。信息不齐也可以生成成果；界面不设置场景通关条件。

界面是只读业务视图。允许浏览、搜索或筛选已展示范围、打开来源、查看版本、复制引用、刷新内容等查看动作；新建项目、上传材料、编辑对象、删除内容、保存意见、确认成果等业务写入由用户在 Codex 中指示 Agent 完成。本稿不增加页面内聊天或评论系统。

浏览某个项目或切换 draft/review，不等于改变 Agent 正在操作的项目，也不等于改变项目的工作场景。每份内容都必须能明确所属项目。用户 review 是阅读并反馈，不等于必须点击“通过”的审批流程。

## 3. 项目列表与项目身份

用户需要能够识别、查找和进入不同项目，不能只有一个固定工作空间项目。

| 信息 | 内容要求 |
| --- | --- |
| 项目名称 | 真实项目名称；同名项目仍有可区分的稳定身份 |
| 最近已保存变更 | 时间及简短变更说明，例如“更新交付细节”；只来自实际保存记录，不写成 Agent 活动状态 |
| 项目标识 | 查看或复制引用时可取得，用于向 Agent 准确指定目标；无需将内部 ID 当作项目名称 |
| 项目概况 | 有已保存背景/客户信息时，可引用对应 draft 内容；不另建一份独立维护的摘要，不因名称猜客户 |

项目内需能识别当前项目，并查看该项目的 draft、review、材料及历史。没有任何内容的新项目也能进入；不把“无内容”解释为故障。

没有项目时，说明可在 Codex 中让 Agent 创建项目。只有实际存在项目归档能力和记录后，才使用“已归档”等业务分类；不能根据日期或未访问时间推断项目结束。当前 `working_scene` 默认值不能被包装成实时进度。

## 4. 信息收集 / draft

### 4.1 所有对象共有的信息

用户应能了解全部 23 类对象的名称和简短作用，并找到已有内容。没有内容的类型无需创建空记录，更不能显示为待完成任务。

对已有对象及其条目，需支持查看：

| 信息 | 内容要求 |
| --- | --- |
| 身份与含义 | 对象名称、业务类型、所属项目、简短职责说明 |
| 当前内容 | 已保存正文及业务字段；同一对象可同时包含文字、结构化信息、图片、文件引用和链接 |
| 信息性质 | 按已保存语义区分来源事实、转述、用户补充、假设、建议和已采用决定；不可把 Agent 推断显示成客户原话 |
| 适用范围 | 已记录的交付轮次、具体资源/创作者或其他限定；局部要求不能被显示成全项目要求 |
| 来源依据 | 来源标题、引用片段、所引用的来源版本及实际可用定位 |
| 关联内容 | 依赖哪些 draft 条目、被哪些对象或 review 段落使用；关系需来自已保存引用 |
| 版本与变更 | 当前版本、实际更新时间、可追溯旧版本和关联变更/决定 |
| 未知与分歧 | 已记录的未知项、不适用说明、冲突说法及各自证据；当前采用口径与原始说法分别保留 |

“尚未记录”“已知但未确认”“不适用”不是同义词。不适用或未确认需要实际依据，不能由空字段推断。金额以用户能理解的金额和币种展示，日期/区间保留精度和时区（如有），未知值不显示为零。

### 4.2 全部 23 类对象的信息清单

下表列出业务阅读内容，不要求某种排布或特定图表。未取得的信息可以缺省；精确可存字段仍以对象契约为准，不能为匹配 UI 样例编造数据。

| 编号 / 对象 | 需要支持查看的业务内容 | 必须能辨别的边界 |
| --- | --- | --- |
| D01 BD 同步信息 | 背景、客户为何现在做、目标、核心问题、决策标准、偏好及依据 | 客户说法、BD 判断与当前采用口径 |
| D02 客户原始 Brief | 原件标题/版本、原文入口、提取的需求与原文定位 | 客户原文与后来的解读、补充、纠正 |
| D03 招标文件 | 原件与版本、范围、交付和评审要求，以及与其他需求材料的差异 | 原始招标要求与项目采用的解释 |
| D04 场地资料 | 地址、图纸、照片、已知场地条件、尺寸/限制及来源 | 实测或核实信息与未核实描述 |
| D05 甲方客户品牌资料 | 品牌定位、文化资产、核心信息、视觉规范、相关文件与图片 | 品牌材料原件与提取结论；使用条件关联交付细节 |
| D06 受众 | 受众描述、需求、触达点和依据 | 现场观众与传播受众；已知信息与假设 |
| D07 总预算区间 | 金额/区间、币种、预算口径、不同来源说法、当前采用值及决定 | 客户原始预算与本轮采用预算，不覆盖历史说法 |
| D08 策划预算分配 | 分配内容、投入重点、克制项、建议与已采用分配、实际审查意见 | 预估、报价、分配建议与已采用分配 |
| D09 时间节点或区间 | 事件、日期/区间、相关交付、Review 节点关注内容、倒排依据 | 明确日期与估计区间；不重复维护交付规格 |
| D10 客户关键决策节点 | 客户侧角色、谁决定什么、待客户确认事项、双方决策边界 | 客户决策角色与 D20 内部职责 |
| D11 合作类型 | 竞标、委托、咨询、执行追加等实际类型及说明、依据 | 已确定合作方式与待确认说法 |
| D12 竞争对手分析 | 竞争对象、公开作品、引用材料、分析和判断 | 核实信息与传闻、推测 |
| D13 客户历史合作方与过往项目 | 历史项目、合作方、作品/媒体、表达特点及来源 | 历史事实与对本次偏好的推断 |
| D14 与甲方的会议纪要 | 原始纪要/转写、会议时间（如有）、客户原话、议题、意见与实际决定 | 原话、摘要、意见、已作决定；实际可用的段落/时间定位 |
| D15 客户 Q&A 问题表 | 问题、涉及对象、跟进人、答复、证据、已记录状态 | 无答复与已有答复；答复关联到哪些业务对象 |
| D16 立项评估结果 | 档期、资源、供应商、投入及价值匹配判断、依据 | Agent/用户建议与真实正式评估 |
| D17 主策策略 | 本轮目标、策略、调研判断、已有方向候选、取舍理由、实际审查意见 | 已有策略与待讨论建议；不要求必须完成创意方向筛选 |
| D18 交付细节 | 轮次、交付物、颗粒度、格式/规格、数量、使用限制、外部依赖、不做范围、适用资源 | 本轮/某位创作者要求与全项目要求；日期引用 D09 |
| D19 内外部资源 | 人员/机构、能力、作品依据、档期条件、参与情况 | 候选、已核实可用、已确认参与 |
| D20 职责边界 | 主策、专业负责人、BD 接口、内部拍板人、任务职责与协作接口 | 建议分工与实际承接；不与客户决策角色混用 |
| D21 项目评级 | 评级、理由、来源和确认依据 | 建议评级与正式评级 |
| D22 风险点 | 风险描述、触发条件、影响、应对建议、待核实事项、接受/处理决定 | 风险线索、判断与实际处理决定 |
| D23 评审会结论 | 实际立项评审结论、Go/No-Go、补材料/调整交付/重新评估等决定及行动项 | 立项评审与创意审查；这是业务记录，不是软件准入门槛 |

内部 `expression_guide` 作为“成果编写要求”可追溯：显示用户的表达/结构要求、作用于哪份成果和哪些段落、指令来源和版本。它不是第 24 类业务对象，不必要求用户理解其技术名称。

## 5. 信息整理 / review

### 5.1 成果共有信息

每份已有成果需支持查看：名称、成果类型、所属项目、实际适用轮次/资源、完整正文、当前版本、实际更新时间，以及段落对应的 draft 依据。不能为了界面呈现把完整成果降为几个摘要字段。

正文应保留已有标题、段落、列表、表格、图片和引用等内容语义。未知、分歧和建议在成果中如实呈现。一个成果类型可以有多个实际实例，例如不同创作者、不同轮次的 Brief，不能只按类型保留一份。

| 成果 | 需要看到的内容 | 主要回溯对象 |
| --- | --- | --- |
| R01 主策 Debrief | 客户为何做、要解决什么、面向谁、谁决定什么、本轮交付与边界的完整说明 | D01、D02/D03、D06、D10、D20、D18，其他按实际引用 |
| R02 推进要素 | 本轮交付、颗粒度、回收/合稿/Review 节点、相关职责和已有待讨论项 | D09、D18、D20、D15 |
| R03 创意审查结果 | 目标、方向、投入重点的实际审查意见、取舍及依据；无正式结论时的已有策略和待讨论内容 | D17、D08，按需关联预算、评估、评级、风险 |
| R04 内外部创作者 Brief | 指定创作者/资源和轮次的任务背景、问题、交付要求、日期、职责、协作及使用边界 | D23、D19、D18、D01/D06/D17、D20、D09 |
| R05 客户 Q&A | D15 同一份问题、答复、状态、来源和关联对象 | 直接使用 D15；不能复制一份独立维护的 review Q&A |

无成果时说明“尚未生成，可让 Agent 基于已有对象整理”，不显示“信息不完整，禁止进入”。R03 名称中的审查结果不能让尚未作出的判断看起来已通过。

### 5.2 依据变化与用户反馈

用户需要区分：正在看的成果版本、该版本实际使用的 draft 内容、draft 当前内容，以及哪些段落的依据已发生有效变化。

- 有可验证的依赖变化时显示“依据已变化／成果尚未同步”，并能查看受影响对象和段落。
- 依据的无关条目更新，不应把所有成果都标成过期；不能只比较整个对象的版本号就断言段落失效。
- draft 已保存但 review 尚未更新时，仍可读旧成果，并明确两者尚未一致；不推断 Agent 正在生成或生成失败。
- 已发布新成果可以查看旧版本；旧来源、旧决定和旧成果不因新版本而消失。
- 用户可以复制所指段落的引用，在 Codex 中反馈。反馈从任何一步进入，最终遵守先改 draft、再更新 review。
- “用户已确认”“已通过”“待重新确认”等审核历史只能来自真实保存的确认记录。当前尚无该持久化能力，不展示推定审核状态。

## 6. 材料与来源

同一来源可被多个对象使用。项目材料信息与对象里的来源引用必须指向同一来源身份，不能成为两份材料库。

| 信息 | 需要支持查看的内容 |
| --- | --- |
| 基础身份 | 真实标题、来源种类（飞书、本地文件、用户口述/补充、网页等）、资源类型、所属项目 |
| 来源入口 | 飞书/网页原文链接，或本地已留存文件的查看入口；原始路径只作为来源信息，不替代留存副本 |
| 保存内容 | 实际保存的文字、文件、图片、视频等；仅有附件时不声称正文已读取 |
| 采集范围 | 全部还是节选、实际页码/区块/时间定位；未取得定位时不编造 |
| 版本与时间 | 当前查看的本地快照版本、采集时间、实际保存时间、已取得的远端 revision（如有） |
| 原文与引用 | 当前对象引用的片段及所用版本，能查看该版本实际保存的来源内容 |
| 归属与处理方式 | 真实提供者/说话者（如有），口述原话、转写、摘录或摘要的性质 |
| 被使用情况 | 引用了该来源的 draft 对象/条目，及沿这些关系可追溯的 review 内容 |
| 文件可用性 | 文件名、类型、大小（如有）、本地副本或外部引用，以及实际检测到的无法访问/已变化信息 |

“最新已收录版本”不等于飞书当前最新版本。历史引用应打开其实际依据的快照，而不是悄悄替换为当前头版本。来源整体头版本与额外保存的节选也需区分。

### 6.1 飞书标题与打开行为

- 已获取标题时展示实际文档标题，不要求用户阅读一串 URL；实际地址仍可查看或复制。
- 点击原文标题，在 Codex 内置浏览器的新标签页打开飞书文档，保留 Yu+ 原内容；此行为已由用户在当前环境验证，正式页面需回归。
- “打开飞书原文”与“查看 Yu+ 保存的来源快照”是不同动作，目的地必须清楚。
- 标题来自本地保存的真实元信息，不要求每次浏览都请求飞书。标题未知时使用诚实的来源描述与可辨识地址，不凭空起标题。
- 文档改名不改变来源身份；历史快照保留当时标题。浏览器登录与 CLI 读取权限分别处理。

### 6.2 多媒体与无法预览的材料

用户应能查看已保存的图片，阅读可支持的文本/PDF，打开或播放受支持的音视频，并知道它们被哪个对象引用。具体预览器和播放控件不在本稿选型。

不支持内嵌预览的格式，应仍可看到真实文件信息并取得可打开的文件，而不是隐藏材料。外部引用文件丢失时，保留来源及关联记录，说明文件当前不可用。本地资产浏览能力仍需前端和只读服务实现。

不设置“已登记、读取中、部分读取、已处理”等 Agent 材料处理状态。采集范围、文件可用性是可核实事实，不能被解释为 Agent 的工作进度。

## 7. 关联追溯与交给 Agent 的引用

用户应能完成以下查看路径；不规定使用独立页面、展开层或其他布局，也不要求关系图：

1. review 段落 → 其使用的 draft 条目及版本 → 原始来源及实际定位。
2. draft 条目 → 依赖的其他 draft 内容 → 引用它的成果及具体段落。
3. 材料来源 → 使用它的 draft 条目 → 相关成果。
4. 一次决定/变更 → 受影响对象或成果 → 当时版本及当前版本。

关联信息需包含可读名称、关系含义、适用范围及相关版本；只展示真实引用，不把“可能影响”当成已建立关系。前后跳转后应能找回原本阅读的对象/条目，不丢失项目归属。

可复制的引用应携带项目身份、对象/来源身份、条目/段落及所看版本，附可读名称，帮助 Agent 定位用户所指内容。内部 ID 可作为引用信息，不要求在正文大量显示。现阶段不假设网页能主动把消息发给 Codex；用户在 Codex 中提交修改意图。

## 8. 变更、版本与决策历史

### 8.1 已保存变更与版本

需查看实际变更时间、操作者信息（如有）、修改理由、变更对象/条目/段落，以及可追溯的前后版本。显示的是保存结果，不是聊天全文、命令执行过程或 Agent 思考日志。重复提交返回旧回执不算一次新变更。

用户应能阅读历史版本，并对照同一内容的前后值/正文及来源变化；不要求自动生成自然语言差异总结，也不指定差异排布方式。当前查看历史版本时必须明确版本身份，不能与当前内容混淆。

### 8.2 长期决策记录

需要查看决定内容、决定者、记录时间、理由、对应用户指令/材料、受影响条目，以及替代了哪条旧决定（如有）。有实际决定时间时才展示该时间，不能把录入时间当作作决定的时间。

例如客户材料记载“100 万”，主策决定“按 60 万推进”：用户能看到原始说法、当前采用预算、决定依据和相关成果，不得把原件改成 60 万。被替代的决定继续作为历史可读。

决策历史不是共识池；D23 是特定的立项评审对象，也不能替代所有类型的决策记录。

## 9. 缺失、更新与异常信息

| 情况 | 用户需要知道什么 |
| --- | --- |
| 没有项目/材料/对象/成果 | 这是尚未建立或尚未收录，而非流程未通过；说明可在 Codex 中做的对应下一步 |
| 部分字段未知 | 当前没取得什么，不补零、不推定“不适用”、不阻止其他工作 |
| 多个来源冲突 | 各自说法、证据及采用口径（如果已有），不把冲突静默合并 |
| 来源未被对象引用 | 材料仍已保存；不把无引用推定为未读、无用或出错 |
| 已检测到依赖变化 | 具体受影响内容及依据，旧成果仍可阅读 |
| 读取失败/服务不可用 | 页面当前无法获取什么；不得将请求失败渲染成空项目或零条记录 |
| 本地文件缺失或变化 | 实际检测结果；继续保留历史引用 |
| 飞书内容有更新 | 只有未来的真实远端检查提供证据后才显示；当前未检查时不显示“已是最新” |

页面读到的业务内容以成功保存结果为准。可告知查看数据的刷新时间；需要刷新时更新读取结果，不生成 Agent 工作状态。数据读取中的常规等待提示与材料“正在被 Agent 处理”是两回事。

## 10. 现有数据支持与后续能力

这一节用于避免设计时误判，UI example 的选择仍按前面的信息需求判断。所有正式浏览功能都还需要实现前端及只读访问层，当前 CLI 可读不代表网页已可用。

| 信息能力 | 当前依据 | 实现可视化时要补的工作 |
| --- | --- | --- |
| 多项目身份、对象与成果正文 | 已有 project/draft/review 的查询、对象类型目录 | 转为只读展示；列表摘要、更新时间需取真实对象/变更记录，不只依赖最简列表返回 |
| 来源、快照、引用、资产元信息 | 已有 source 查询，支持指定快照及正文，外部资产可用性检查 | 文件只读访问、格式预览；保存副本与外部路径的可访问处理 |
| 段落到 draft/来源的追溯 | 已保存版本、证据、依赖关系 | 将关系解析为可读内容；反向引用需汇总已有关系，当前没有独立 relations 查询命令 |
| 依据已变化 | 当前 review 查询有受影响段落信息，另有依赖检查逻辑 | 展示真实影响；历史成果需按其自身依据解释，不能套用当前成果的影响结果 |
| 旧版本、前后对照、历史导航 | 已保存旧版本和变更记录，可按已知版本读取 | 汇总版本目录、前后对照与定位；当前无通用 diff 或完整版本目录专用命令 |
| 决策历史 | 已有 decisions 查询和相关来源/对象引用 | 解析受影响内容及替代关系，供用户阅读 |
| 飞书远端“内容有更新” | 尚无启动后台 revision 扫描实现 | 后续补真实检测与保存结果，再展示通知；当前不模拟 |
| 用户确认/重新确认历史 | 尚无 review 确认记录的持久化命令 | 后续另行补能力；当前不模拟审核状态 |
| 导出到飞书的成果版本记录 | 尚无导出及其版本记录命令 | 后续记录实际导出标题、链接、成果版本和时间；现阶段普通飞书来源链接不冒充导出记录 |

项目概况直接引用现有 draft；未维护客户等元信息时不新增必填表单。项目归档、页面内写入、自动通知或后台任务监控不因本稿而加入当前界面开发范围。

## 11. 用于挑选 UI example 的内容样本

选例时可用下列内容检验承载能力；这是样本需求，不是组件或风格建议：

| 内容组合 | 要判断的阅读能力 |
| --- | --- |
| 多个项目、同名项目、空项目 | 能否分清项目和当前上下文 |
| 一段较长背景说明，同时引用三份材料 | 能否读正文、辨别信息性质并查看多来源 |
| 场地照片、PDF 图纸、视频及若干场地条件 | 能否让材料与提取信息保持清晰关联 |
| 客户预算 100 万、当前采用 60 万及决策原因 | 能否同时理解原始说法、现值和历史依据 |
| 一份完整创作者 Brief，涉及不同轮次及资源 | 能否阅读长成果，同时辨别适用范围和段落依据 |
| 一个交付条目被三份成果引用 | 能否找到关联内容并返回原阅读位置 |
| draft 已变但 review 仍是旧版 | 能否明确版本与尚未同步的内容，而不误报 Agent 状态 |
| Q&A 有未答、已答及关联对象；部分对象没有内容 | 能否呈现不同信息情况而不造成必填/审批压力 |

一个 UI example 不必覆盖所有信息类型，可以分别参考长内容阅读、材料查看、对象关联和历史追溯的处理方式。示例有编辑器、审批按钮或聊天框，不代表 Yu+ 需要继承这些功能。

## 12. 信息展示验收情境

1. 用户能进入任意项目，准确辨认项目归属；复制的引用也指向该项目。
2. 用户能查看全部 23 类业务对象的作用，并阅读已有对象；空对象不会变成阻塞清单。
3. 用户从 review 的某段交付要求追到对应 D18 条目，再追到原始 Brief 的实际引用版本。
4. 用户能从一份材料找到使用它的对象；同一材料在不同入口保持同一身份。
5. 用户把交付从“成片”改为“概念脚本”后，能依次查看 draft 的实际新值、成果是否已同步及旧版本；无关内容不误标变化。
6. 用户要求“这段简短一点”后，可以追到编写要求及新版成果，业务事实无需伪造变更。
7. 用户能查看“100 万 → 60 万”的采用决定、理由和原始来源，旧记录仍存在。
8. 用户在 draft 和 review 查看的是同一份 D15 Q&A，不产生第二份独立问题数据。
9. 已有标题的飞书链接显示标题；打开远端原文和查看本地快照的目的明确。
10. 未知信息、未生成成果、不支持预览或服务读取失败都得到准确表达，不被显示成 Agent 处理状态或流程门槛。

本轮交付止于信息展示规范，供用户挑选 UI example。页面布局、视觉设计、组件选型和实施计划在选例讨论后再确定。
