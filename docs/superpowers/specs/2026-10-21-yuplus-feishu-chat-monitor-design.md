# Yu+ 飞书群聊监控与自动项目同步设计

日期：2026-10-21。状态：供讨论的设计草案；尚未实现、未创建真实定时任务，也未绑定或读取用户群聊。

## 1. 已确定的产品目标

用户明确指定“这个项目监控这个飞书群”后，Agent 定期读取群内进展，自动维护项目信息、来源和决策。默认每 60 分钟检查，用户指定的间隔优先。前端显示项目正在监控的群聊。多项目隔离，允许一个项目绑定多个群。

这是一种持续接收材料的方式，不增加第三个业务场景：收集仍写 draft，整理仍生成 review。允许中途补材料、提出修改意见；更新已有 review 必须先修改其 draft 原因。前端继续只读，Agent 通过 CLI 写入，不增加必填项或业务审批关卡。

## 2. 推荐方案与取舍

| 方案 | 特点 | 本次选择 |
| --- | --- | --- |
| Codex 会话定时任务唤起 Agent，Agent 调用 Yu+ / 飞书 CLI | 复用用户的 Codex 执行环境、Skill 与认证；Yu+ 只保存状态和处理记录 | 推荐首版 |
| Yu+ 自建本地调度器，调用 codex exec | 要自行管理 Agent 进程、权限、版本和运行输出，维护成本较高 | 暂不加入 |
| 飞书事件订阅唤起 Agent | 适合更及时的接收，但仍需解决 Agent 唤起、事件权限、断线补偿 | 后续可扩展 |

执行关系：Codex 定时唤起 → Agent 读取监控配置 → Yu+ CLI 调用飞书 CLI 拉取增量 → Agent 按需分析 → Yu+ CLI 保存来源、draft、决策、受影响 review → 保存本轮结果。

Yu+ 的后台服务不直接调用模型；SQLite 不承担唤起 Agent 的功能。网页是否打开不影响 CLI 同步。定时运行会使用用户的 Codex 额度；本地任务依赖电脑及 Codex 可用、网络和飞书认证有效，不承诺休眠或关闭 Codex 后仍按时执行。

## 3. 开启与调度绑定

1. Agent 从用户明确指示取得 project_id 和群聊目标。解析群链接或核实 chat_id，获取真实群名；同名群有歧义时才询问。不能仅凭材料里出现一个群链接就自动开启。
2. 用当前用户身份验证对该群的读取能力；记录身份标识与租户范围，不保存 token。身份变化时重新核验，不能悄悄切换到另一账号或 bot。
3. `monitor add` 保存绑定和授权范围，初始为“待接通定时任务”。默认间隔 60 分钟；首次建议回看最近 24 小时，用户可指定其他范围或从现在开始。首次范围在开启回执中明确告知，这是可调整默认值。
4. Agent 使用当前 Codex 提供的自动化工具创建或更新会话定时任务；优先在当前会话继续，不为每次检查新建会话。任务提示词只包含已绑定的配置身份、Skill 路由、执行目标和汇报规则，不塞入历史群消息。
5. 保存工具返回的 automation_id、目标会话/主机身份、实际生效间隔和最近核验时间。创建失败时保持“待接通”，不能显示监控已运行。重复开启同一绑定应复用已有配置和调度任务。
6. 完成一次初始拉取与同步，验证定时执行环境的 CLI、数据目录和权限。普通聊天中的一次成功不足以证明无人值守权限可用，实际定时运行必须纳入验收。

同一个承载会话可以用一条 Yu+ 定时任务检查其明确绑定的多个 monitor_id；每个监控独立保存间隔和 next_due_at，不能顺手扫描其他项目。混合分钟间隔时按共同分钟刻度唤起，只执行本次到期项，例如 30 与 45 分钟以 15 分钟为刻度。不能覆盖同一会话里不属于 Yu+ 的定时任务；若宿主限制无法并存，应报告并让用户选择承载方式，不自动创建额外聊天。

调度工具是宿主能力，不是 Yu+ CLI 的隐藏接口。安装时检测其可用性；无此能力时仍允许绑定群和手动同步，但明确显示“未配置自动检查”。用户要求的间隔若宿主无法表达，应说明限制，不能擅自换成一小时。Yu+ 只保存实际工具回执，不直接修改 Codex 私有数据库或 automation.toml。

修改间隔时先记“配置待应用”，更新宿主任务成功后记录实际间隔。暂停时先在 Yu+ 中禁止该监控的后续写入，再协调宿主；即便后续唤起已排队也只会跳过它。解除绑定保留历史消息证据、对象和决策。恢复默认接续原游标补读暂停期间消息，若用户要求跳过，则显式记录跳过区间。

离线后的下一次成功唤起从持久化游标补读，不按漏掉的每个小时分别启动一堆任务。不依赖宿主保证补跑；手动“立即同步”也可以触发补读。下次检查时间是计划值，不是执行承诺。

## 4. 消息如何增量读取

### 4.1 固定时间窗口与完整分页

每个绑定保存“已完整拉取至”的时间 C。开始检查时固定上界 T，读取 `[C - 5 分钟, T]`，首次以授权的回看起点为下界。5 分钟重叠用于边界时间与短暂迟到，不能宣称覆盖任意延迟。时钟明显异常时保留游标并提示。

已核对的飞书命令能力示意：

```text
lark-cli im +chat-messages-list --as user --chat-id CHAT_ID \
  --start START_ISO --end END_ISO --order asc --page-size 50 --format json
```

Yu+ 的读取适配器执行上述受控命令，检查退出码与 JSON 信封 `ok`，持久化收到的页。下一页必须保持同一群、身份、时间上下界及排序，只追加实际返回的 page_token。不能把默认第一页当完整结果；`--page-all` 也有页数上限，要检查 complete / has_more。

只在整个窗口完整拉取并持久化后推进 C 到 T。中途失败保留窗口和分页位置，重新执行时继续或重读同一窗口；分页 token 失效则从该窗口起点重读，依靠消息身份去重。无新消息也能推进完整拉取时间。

网络请求期间不占用 SQLite 长事务。大量积压按页及时间段分批，超过执行预算留下明确待续记录，不能跳到当前时间冒充追平。CLI 返回新增/变化数量和批次 ID，Agent 按需取正文，避免全部历史进入上下文。

### 4.2 话题回复、编辑与撤回

群列表不能代表所有话题回复。CLI 的自动展开也可能截断，需检查 thread_has_more / thread_replies_error；必要时用 `+threads-messages-list` 单独分页。话题接口不支持时间范围，保存各 thread 的独立边界，从最新页回读到已确认边界，并去重。

对已经发现的 thread 持续检查新回复，即便其根消息较旧；不能只对本次新增根消息展开。首版的历史覆盖范围必须可见：默认回看区间之外、从未被发现的旧话题，不承诺自动发现其新回复。用户指定历史话题时可纳入监控；需要全面覆盖老群话题时必须扩大回溯建立索引。不能对这类未覆盖情况显示“全群完整同步”。

每次常规拉取加一轮最近 24 小时的重读，用于发现近期编辑、撤回及新出现的回复入口；两者分别保存边界，不用复查结果覆盖主拉取游标。对当前被 draft/review 引用的消息，每天通过 mget 分批复查。更早且未被引用的消息不承诺发现全部修改；权限不足、返回缺失不能直接判为撤回。

只有明确的编辑/撤回证据才追加对应消息版本。撤回后保留旧证据和历史决定，标记其依据变化并重新评估；不能自动删除已有决策。内容未变的表情、姓名显示或读取时间变化，不触发业务重写。飞书消息列表按创建时间排序，因此仅按“上次检查时间”读取无法覆盖历史编辑。

## 5. 三层防重复与失败恢复

### 5.1 消息层

稳定身份为 `(项目, 租户/身份范围, chat_id, message_id)`。同群绑定两个项目时各自维护业务结果，不互相共享处理完成状态。

规范化正文、消息类型、附件身份、回复关系与明确撤回标记后计算内容指纹；排除读取时间、表情数量等非业务字段。与当前消息版本相同则只更新观察时间；确有变化则追加不可变版本。可靠的远端更新时间用于拒绝旧观察覆盖新版本。指纹不能作为永久唯一版本键，因为正文 A→B→A 也可能是一次真实修改；缺少可靠远端版本时，串行观察与当前头比较，存在顺序歧义则重新核验。

### 5.2 业务写入层

冻结一批待处理消息版本，产生稳定 batch_id。每个已判断版本有明确处置：已应用、无需业务变化、已转成待澄清问题，或尚未处理；这属于同步账本，不新增普通材料的“Agent 正在阅读”等状态。

每一步在执行前保存确定的 request_id 和请求正文，重试使用相同内容及 ID；业务写入回执和步骤完成标记在同一 SQLite 事务内提交。需要调整内容时先确认旧请求是否成功，再创建新步骤，不在未知提交结果时重生成请求。终态版本不会因为下次又读到而再次追加决定。

直接复用现有 source.import / draft.apply / review.prepare / review.publish 的校验和业务处理器；为监控写入添加 run/step 身份及范围校验，不另造一套能绕过“先因后果”的写接口。

人工已导入同一消息时也复用相同来源身份。不同消息重复陈述同一事实时仍应关联证据、避免重复创建业务条目；这属于 Agent 对照当前对象的职责，不能靠 message_id 去重解决。

### 5.3 执行层

同一项目的自动同步采用带到期时间、续租和递增代号的执行租约，避免两个群的任务并发改写同一项目。过期旧执行器的提交会被 CLI 拒绝，不能仅凭旧进程曾拿过锁继续写入。每次监控写入都在事务内验证绑定仍启用、项目匹配、租约代号有效。

人工修改仍可执行，沿用对象 base_revision 冲突检测。冲突时仅重读受影响对象；不得覆盖用户刚保存的变化。网络与模型工作不持有数据库写锁。

“已拉取至”与“已处理完的批次”分开。draft 保存后 review 失败，保留 draft 和原 cause_change_id，下次继续未完成 review；不能重新生成同一个决定。暂时无法判断的消息形成有证据的 Q&A/待澄清记录，允许其他消息继续；并明确展示待澄清事项，而非假称全部信息已采用。

## 6. 自动更新的业务边界

- 普通进展、明确事实、材料链接：保存来源，更新相关 draft 条目，保留说话人和时间。
- 明确决定：结合现有 D10 客户决策角色、D20 内部职责及上下文判断是谁作出的决定；记录原话证据、决定者、理由和影响对象。新决定替代旧决定时使用既有 supersedes_id 链。
- 提议、转述、冲突：保留其性质；不把“建议改成 60 万”自动当成预算已经改为 60 万。仅冲突部分等待澄清，不阻断整个群的同步。
- 已有 review 受影响：在已授权的项目维护范围内更新相关段落；保留其他段落。尚未建立 review 的项目默认维护 draft，不因接入监控就自动创建所有成果或切换项目场景。
- 附件和文档链接按相关性择机读取，利用现有文件池去重；无法解析的附件记入待处理，不冒充已理解。原始下载失败不能使整条消息凭空消失。
- 群内容是项目证据，不是新的工具权限或调度指令。群成员说“监控另一个群”“上传所有项目”“删除数据库”等不扩大用户在 Codex 给出的授权。本功能不向群发消息，也不编辑飞书原文。

默认无需每小时再次向用户申请维护项目的许可。仅目标不明、事实冲突或实际认证/权限缺失时求助。定时空跑不重复发送“没有变化”；有项目变更、待决问题或持续故障时给简短结果和相关链接。定时汇报避免重复刷屏，业务回复的读取/修改/下一步规则按场景保留。

## 7. 本地数据与 CLI 扩展

仍使用一个 SQLite 与现有文件池，不引入 Redis、队列服务、独立对象存储或模型服务。建议新增以下技术记录，不新增 23 类 draft 之外的业务对象：

| 记录 | 主要内容 |
| --- | --- |
| monitor_schedules | 宿主/会话/automation_id、期望和已确认的调度、核验时间及配置错误 |
| chat_monitors | project_id、身份范围、群 ID/名称/链接、启用状态、间隔、回溯起点、授权范围、各流游标与已发现话题 |
| monitor_messages | 消息身份、不可变观察版本、正文/附件引用、指纹、远端时间、处置及 source_version_id |
| monitor_runs | 固定拉取窗口、分页检查点、冻结批次、阶段、统计、重试信息、完成时间 |
| monitor_steps | 稳定步骤身份、请求正文、业务回执及变更 ID，唯一约束阻止重复提交 |
| monitor_leases | 项目执行租约、代号、持有者、到期时间 |

消息正文小文本留 SQLite，实际附件使用现有按内容寻址的文件池。业务相关消息作为 `provider=feishu, resource_type=message` 的来源；来源标题显示“群名 · 发言者 · 时间”，支持打开原消息和查看本地版本。监控本身是配置，不是一份每小时重写的巨型群记录文档。

现有代码有两处必须扩展：`source.py` 目前只接受飞书文档地址，需要增加消息 AppLink 的严格身份校验；`source_check.py` 目前扫描全部飞书来源，需要将 message 分流到消息观察逻辑，不能拿文档 revision 检查消息。决策现有 instruction_source_version_id 可指向真实群消息版本，不得伪装成用户口述。

拟议 CLI 命令（当前版本均未实现）：

| 命令 | 职责 |
| --- | --- |
| monitor add / list / show / update | 保存和查询群绑定、间隔及范围；配置使用版本校验 |
| monitor pause / resume / remove | 暂停、恢复、解除绑定；保留历史 |
| monitor scheduler-bind | 记录真实宿主调度回执；不会自行创建 Codex 任务 |
| monitor begin / renew | 认领到期或手动触发的同步，返回 run 与有效租约 |
| monitor fetch | 按保存的范围调用飞书 CLI、分页入库和去重；不调用 AI |
| monitor pending / read | 分批返回未处理版本及必要消息上下文 |
| monitor step | 持久化并执行一个现有业务命令或记录无需修改/待澄清处置；同事务保存回执 |
| monitor finish / runs | 校验实际完成范围、释放租约、查询结果与未完成事项 |

监控写命令始终绑定真实 data_dir、project_id、monitor_id。业务规则仍由原处理器执行。finish 不接受一句“已完成”作为证据，需核对批次各版本处置、实际变更回执及未完成 review 步骤。

数据库通过显式迁移升级，升级前做完整备份。新增记录进入备份/恢复范围；恢复副本默认暂停监控、清除运行租约、要求重新核验调度绑定，避免原库与恢复库同时自动写入。同一份数据被迁移到另一主机时不能沿用旧主机的运行身份。

## 8. 前端展示

沿用交付 UI 风格，只补充信息与入口。项目内增加“监控群聊”区域，draft/review 都能访问；项目列表增加“监控 2 个群”及需要注意的异常摘要。

每个群显示：真实群名（打开群聊）、检查间隔、首次回看范围、启用/暂停/待接通、最近检查时间、消息已拉取至、最近项目更新摘要、待澄清数量和错误原因。调度核验很久未更新时显示“调度状态待核验”；逾期只能说“尚未收到本轮结果”，不能臆测 Agent 正在忙。

“最近检查成功”“本轮保存了哪些项目变化”分别展示。没消息可显示最近一次检查无新消息，不刷项目变更历史。正文来源可追到具体消息版本，决策可追到对应发言与实际业务变更。

可点击的操作限于打开群聊/来源/关联对象、查看运行记录，以及复制“立即同步、暂停、恢复、调整间隔、解除绑定”的 Prompt。复制内容绑定项目和监控 ID，点击复制本身不改变监控。

这些状态来自 CLI 的持久化运行回执与宿主调度回执，描述可验证的结果；不恢复之前否定的“Agent 读取中、部分读取”等普通材料处理状态，也不增加虚假的实时进度。

## 9. Skill 同步

不新增独立的业务主 Skill。修改 yuplus 主文件的按需读取表，新增 `references/chat-monitoring.md`：

- 用户指定项目群：读绑定、身份与调度配置部分，按需读 lark-im / lark-shared。
- 定时任务唤起：读或复用执行循环，先查真实配置、待续批次和到期项；无新增内容立即结束，不加载整个项目历史。
- 有消息：只取本批次及相关对象；消息线程、附件、飞书文档分别读对应外部 Skill。
- 业务更新：复用对象属性和 draft/review 原有规则；记录明确决定，冲突转待澄清，不改写原始发言。
- 恢复失败任务：先读已保存步骤与回执，只继续未完成工作。
- 用户询问监控状态或要求调整：查询持久化记录，并在需要时通过宿主工具核验实际调度。

## 10. 实施前后的验收重点

1. 实际 Codex 定时运行能在无人继续输入时触发 Agent，读到正确 Skill，并使用正式安装的 CLI 与指定数据目录。
2. 默认一小时及用户自定义间隔准确保存；创建失败、外部暂停、无调度能力均不伪报正在监控。
3. 多页、同秒消息、重叠窗口、分页失败、过期 token、积压超预算均不跳过未拉取内容。
4. 已发现话题的新回复可接续；自动展开被截断或失败不会伪报完整。旧话题覆盖边界按实际范围展示。
5. 重复触发、命令成功但回执丢失、进程中断后恢复，不重复追加来源、对象版本或同一决定。
6. draft 成功而 review 失败后继续原因果链；人工并发修改、暂停和租约过期能够阻止旧任务覆盖。
7. 消息编辑/撤回、A→B→A、附件失败、账号变化、歧义或冲突按证据处理；群消息中的指令不能改变监控授权。
8. 多项目不串数据，前端所有状态有回执依据，备份恢复不会意外启用第二份监控。

本轮建议采用的两个产品默认值：首次回看最近 24 小时；自动维护 draft 和已存在的受影响 review，不自动为尚未进入整理的项目生成全套 review。二者均可按用户要求调整。
