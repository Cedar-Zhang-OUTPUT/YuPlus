# Turn group conversation into useful project evidence

Read when interpreting a fetched group batch, choosing sources, or processing its attachments. This is a semantic task for the Agent; the CLI preserves evidence and receipts, not topic boundaries. Reuse guidance already read.

## Read a discussion before deciding what it means

The fetched message queue is operational history, not the user's material library. Fetching all accessible history does **not** mean capturing every message as a source or creating one draft item per message.

Read adjacent turns, participants, replies, dates and linked materials together. Form a segment around a coherent project issue or decision episode: a proposal, clarification, disagreement and response that belong together. A time gap or page boundary alone is not a topic boundary. Keep distinct topics and successive decisions distinguishable; never collapse a later reversal into an earlier “consensus”. “Yes”, “the latest one”, an @mention or an image placeholder needs its antecedent before it supports a claim. A standalone authoritative statement can be a one-message segment when its meaning and scope are actually self-contained.

Use `pending limit` up to 100 when a 25-message batch cuts through a discussion; do not resolve a turn before reading the context it needs. The current CLI exposes only the oldest 100 unresolved messages. For a discussion longer than that, preserve a clearly titled bounded continuation with its context and uncertainty, carry that context forward, and link the next segment in draft evidence. Do not call a page-sized fragment a complete decision or discard intervening messages just to reach a later answer.

System notices, greetings, acknowledgments, duplicates and unrelated chat usually remain only in the queue and are resolved `no_change` with a truthful reason. Do not manufacture a source, draft item or decision to obtain a receipt. Context-bearing acknowledgments belong inside the relevant segment, not as separate material cards. “Process all history” means every message receives appropriate consideration/disposition, not that every message becomes business data.

## Two material shapes

**Discussion segment.** Use grouped `monitor capture` with the actual `message_versions` and a readable topic title, e.g. “12月11日 · After Party 与晚宴形式确认”. It stores one `chat_segment` source containing the selected original turns in order, speakers/times and verified Feishu locators. Its scope is that bounded segment, not the entire chat. Do not replace the transcript with your interpretation; the interpretation belongs in draft. Reuse the returned source version for all supported draft facts/decisions, with locators for the relevant participant/turn. For a decision, keep the actual decision maker, timing, authority and any conditions; a question or suggested option is not an adopted decision. Raw transport tags may remain in the verbatim source, never in the business object's prose.

**Independent file/document/minutes.** Treat each actual material as its own source, separate from its sending message. Retrieve the relevant original bytes or a faithful document/minutes export with the installed Feishu Skill, inspect it with an appropriate reader, and copy the resulting file into Yu+ using `assets[].storage="copy"`. A `file_key`, cloud URL or screenshot placeholder is an address to retrieve content, not the content itself. Do not merely paste the address into a Brief item and claim the attachment has been processed.

- Group attachments/images: use installed `lark-im` resource-download guidance, then the matching file/image/PDF reader. Use `lark-drive` for Drive files. Keep the actual filename, MIME type and original bytes. A locally saved message attachment can use `provider=local`, a real `resource_type` such as `file`/`image`, and a stable provider key derived from its actual remote identity; first check for an existing source. Technical identity stays in metadata.
- Cloud documents/wiki: use `lark-doc` and, when needed, `lark-drive` to resolve/read/export the resource. Keep its Feishu identity, canonical document URL and known revision, with the real local export as a copied asset on that **same** source. Do not create separate independently maintained “link” and “download” duplicates. If only complete fetched Markdown is available, save a faithful `.md` file and label it a Markdown capture, not an original PDF/DOCX. Retain actual capture scope; an excerpt is not a complete local document.
- Meeting minutes: use the installed `lark-meeting` workflow for the actual minutes/transcript/export; use the relevant document/file reader for the returned artifact. Keep version and event time distinct from download time.
- Preserve the verified sending-message AppLink and available message identity in the asset's `locator` or draft `source_refs[].locator`. If the surrounding discussion explains a material's applicability or adoption, also cite its discussion segment. Use real supported message/thread locators; a verified group fallback must be labeled as group-level, not exact-message positioning. Never invent a deep link from a file key.
- Repeated sends of the same material reuse its source; a genuine revision appends a snapshot. Distinct older proposals and newer Briefs retain their versions and applicability. Sender wording such as “latest” needs context; upload time alone does not establish current authority.
- Permission/download/reading failures remain explicit operational limitations in the conversation/run summary. Keep available links and original queue evidence; do not invent contents, label the failed download as complete, or put HTTP errors, commands or access logs in project objects. If the unavailable material could change the interpretation, leave the affected work unfinished and resumable rather than falsely resolving it as fully applied. A user-confirmed decision to proceed without it can be recorded honestly without claiming it was read.

## Write business meaning, not a message dump

Write one item per coherent business fact, constraint, issue or decision, using the actual fields of the relevant object. Merge supporting turns into that item's evidence instead of duplicating the item per turn. A file belongs to client Brief/BD context only when its read contents support that business role, not merely because it was sent in the group.

Keep `file_key`, `image_key`, `message_id`, resource tokens, raw `<file .../>` tags, `[Image](img_...)` placeholders, download paths, API output and sync logs out of draft/review titles, descriptions, notes and business summaries. Use source/asset metadata, evidence locators and monitor receipts for technical identifiers. This restriction does not erase business-relevant version names, deliverable filenames or verbatim raw evidence.

Example: “快闪日也有晚宴？” followed by the responsible person's “是的” can support “活动形式：快闪日包含晚宴”, citing the conversation segment with both turns. It should not produce separate “活动形式讨论” items containing an image key, the question alone and “是的”. A string `<file key="..." name="2026 Brief.pdf"/>` prompts retrieval of that PDF; only its actual contents support Brief requirements. “最新版的 Brief” should be associated with the material being referred to, not copied into a standalone requirement.

Before saving, check: does the item tell the planner something about the project, can the cited context justify it, and can the user open the underlying material? Read back the affected objects after saving to catch pasted tags and detached replies. Preserve draft-first review updates and existing version history. When explicitly correcting prior noisy output, update the affected current items and review, preserving their old versions; do not delete original sources/history or directly edit SQLite. This capability does not automatically clean already-imported projects.
