# Yu+ 对象属性与成果关系

这是业务含义参考，不是建档清单。只读本次涉及的条目；精确写入字段通过 `scripts/inspect_contract.py` 查询已安装版本。本文业务属性来自随应用维护的 `object-types.json`；版本不一致时用 `yu types show --type TYPE --json` 核实。

产品当前只有信息收集（draft）、信息整理（review）两个场景。收集时读取材料并将已有信息落到 draft 对象，保留来源与关联；整理时，AI 根据已有 draft 信息组织、改写成 review 成果。source 是来源证据层。review 有修改要求时先改 draft，再更新成果；两个场景均可随时补充材料或接收修改意见，沿来源 → draft → review 更新，并将成果交回用户 review，形成持续循环。

所有业务对象都允许未知、不适用和稍后补充。下游列表表示可能关联，不代表每次都必须建立全部关系。展示方式描述业务语义；实际页面入口与控件查阅独立 yuplus-visualization Skill。

## Draft 属性

source 保存取得的材料及版本，draft 保存带依据的项目内容。文件、图片和视频在来源资产中保存；draft 引用对应来源版本、资产和实际定位。不要把一份上传文件误当成已经分析完毕的结构化内容。

### D01 BD 同步信息（`bd_context`）

- 含义与边界：项目背景、客户为何现在做、目标与核心问题、决策标准和偏好；区分客户原话、BD 判断与用户采用口径。
- 可能来源：BD 口述/文档，D02、D03、D14；需要客户回答的业务缺口关联 D15。
- 展示语义：分主题正文与原话引用，标明信息性质。
- 可能影响：R01 主策 Debrief、D17 主策策略。

### D02 客户原始 Brief（`client_brief`）

- 含义与边界：原始材料引用、版本，以及从中提取的需求条目；用户纠正单独保存，不伪装成客户原文。
- 可能来源：客户文件或飞书文档；条目关联 D01、D06、D07、D09、D18 等。
- 展示语义：原件预览与需求条目对照。
- 可能影响：R01；其他 draft 对象的证据。

### D03 招标文件（`tender_documents`）

- 含义与边界：原件引用、版本、范围/交付/评审等要求及差异说明。
- 可能来源：招标原始材料；与 D02、D01 对照。
- 展示语义：文件预览、要求清单和原文定位。
- 可能影响：R01；D09、D10、D18 等。

### D04 场地资料（`venue`）

- 含义与边界：图纸、照片、地址等材料集合，以及有依据的场地条件；未核实尺寸不填成事实。
- 可能来源：本地/飞书材料、可核实公开资料。
- 展示语义：图片/图纸预览与场地条件说明。
- 可能影响：D17、D22；R01 按实际需要引用。

### D05 甲方客户品牌资料（`brand_assets`）

- 含义与边界：品牌材料集合、定位、文化资产、核心信息与视觉规范；资产使用条件关联 D18。
- 可能来源：品牌文件、客户公开资料。
- 展示语义：材料集合、视觉预览与主题摘要。
- 可能影响：D17；R01 按需引用。

### D06 受众（`audience`）

- 含义与边界：现场观众与传播受众分别记录；画像、需求、触达点及依据。
- 可能来源：D01、D02、D14；AI 假设单独注明。
- 展示语义：两类受众卡片或正文，附来源。
- 可能影响：R01、D17。

### D07 总预算区间（`budget_range`）

- 含义与边界：客户预算、期望区间、币种及口径；保留不同说法和本轮采用值。
- 可能来源：D01、D02、D03、D14，用户明确决定。
- 展示语义：预算字段、来源说法对照、当前采用口径。
- 可能影响：D08、D22；R01/R03 按需引用。

### D08 策划预算分配（`budget_allocation`）

- 含义与边界：投入重点、克制项、分配建议与已采用分配；预估与报价分开；相关实际审查意见。
- 可能来源：D07、D19、D23，用户评审意见。
- 展示语义：可编辑对象的只读分配表与说明，来源及决定记录。
- 可能影响：R03 创意审查结果、D17。

### D09 时间节点或区间（`milestones`）

- 含义与边界：事件、日期/区间、对应交付及 Review 看什么；倒排结果注明依据。
- 可能来源：D02、D03、D14、用户安排，关联 D18/D20。
- 展示语义：有具体日期/时刻或完整起止区间的事项必须进入甘特图；只有无法定位到日历的时间说明保留为图下文字条目。
- 可能影响：R02 推进要素；其他成果直接引用日期。

**写入 D09 时按下列规则保存，不能只把日期写进 event / note：**

- 每个可定位到日历的节点或连续区间保存为独立条目：`event` 为事项名称；日期点使用 `time_kind="date"` 与 `start="YYYY-MM-DD"`；具体时刻使用 `time_kind="instant"` 与带实际时区偏移的 RFC3339 `start`；区间使用 `time_kind="range"` 与 `start/end`。区间两端须同为日期或同为带时区时刻，且结束不早于开始。正式 CLI 没有可写的 `date` 字段。
- 一段材料含多个不连续日期/区间时逐个拆分，不能把整串日期塞进一条 note，也不能合并成一个覆盖中间空档的大区间。例如在来源明确年份为 2026 时，“9.25–9.27、10.1–10.7、10.11、10.17–10.18、10.24–10.25”应形成五条甘特记录。
- 已有具体日期但尚待确认（TBC）、原文排期、团队建议或倒排计划，同样保存结构化时间；在 event / note 和条目的 epistemic_kind、source_refs 中保留其真实性质与依据，不把“能画到图上”说成“客户已确认”。明确撤销日期后不继续当作当前排期；旧时间留在历史与来源里。改期时复用同一事件的 item_id、替换时间，避免新旧两行并列冒充两个事件。
- 只知道“合同后两周”“日期另定”或“14:30–15:00 但不知道哪一天”时保留文字，不补造日期。缺失年份先查已读材料与项目上下文；只有能够明确确定才补全年份，不能默认使用当前年份。只有起点或终点已知时，可把真实已知边界存成相应日期点，不编造另一端。精度到日就保存日期，不补零点；具体时刻需有可依据的时区。
- 原材料与业务正文可以保留原话，但项目排期统一落到 D09 并关联来源；不要另维护一份仅供画图的日程。修复已有纯文字条目时，复用可对应的稳定 item_id；拆分多项时各项保留来源与原说明，移除或改写原汇总条目，避免图表与文字清单重复计数。检查已有依赖，按先 draft 后 review 的规则更新受影响成果。
- 保存后只回读本次相关 D09 内容：核对材料中的每个具体节点/区间都有对应结构化记录，而非只核对总条数或第一项。页面刷新后这些记录会自动进入甘特图，无须修改前端或调用不存在的“加入甘特图”命令。

以下只是 `data` 示例（假设材料明确年份 2026、当地时区 +08:00）；实际写入仍要完整条目、稳定 ID 和真实来源：

```json
[
  {"event":"中秋活动（TBC）","time_kind":"range","start":"2026-09-25","end":"2026-09-27","note":"客户原排期，整体活动期尚待确认"},
  {"event":"国庆活动（TBC）","time_kind":"range","start":"2026-10-01","end":"2026-10-07","note":"客户原排期，整体活动期尚待确认"},
  {"event":"周末活动（TBC）","time_kind":"date","start":"2026-10-11"},
  {"event":"周末活动（TBC）","time_kind":"range","start":"2026-10-17","end":"2026-10-18"},
  {"event":"周末活动（TBC）","time_kind":"range","start":"2026-10-24","end":"2026-10-25"},
  {"event":"回标截止","time_kind":"instant","start":"2026-05-28T18:00:00+08:00"},
  {"event":"方案讨论","time_kind":"range","start":"2026-10-21T14:30:00+08:00","end":"2026-10-21T15:00:00+08:00"},
  {"event":"Brief 沟通时间待定位","note":"14:30–15:00，原截图没有日期；不生成日历节点"}
]
```

负责人使用 `owners` 字符串数组：省略或 `[]` 表示未指定，`["主策"]` 为单人，`["主策", "BD"]` 为多人。仅记录有依据的姓名或角色，不自动指派；同一时间项的负责人随该条目更新，R02 引用同一依据。姓名在甘特图标题后以灰色小字展示。

### D10 客户关键决策节点（`client_decisions`）

- 含义与边界：客户侧谁决定什么、哪些事项待客户确认、双方决策边界。
- 可能来源：D01、D03、D14；决策标准引用 D01。
- 展示语义：决策角色与事项清单。
- 可能影响：R01；相关日期引用 D09。

### D11 合作类型（`cooperation_type`）

- 含义与边界：竞标、直接委托、前期咨询、在执行追加等类型及依据。
- 可能来源：D01、D02、D03。
- 展示语义：简单选项及补充说明。
- 可能影响：D17、D18；R01 按需引用。

### D12 竞争对手分析（`competitor_analysis`）

- 含义与边界：已知竞争对象、公开作品与研究判断；未经核实的名单和推测单独标明。
- 可能来源：D01、D03、公开资料。
- 展示语义：对手卡片、作品引用与分析正文。
- 可能影响：D17；R01/R03 按需引用。

### D13 客户历史合作方与过往项目（`client_history`）

- 含义与边界：历史项目、合作方、表达方式及来源，不直接推定本次偏好。
- 可能来源：客户资料、公开记录、可核实项目资料。
- 展示语义：案例条目、媒体预览与分析。
- 可能影响：D01、D17。

### D14 与甲方的会议纪要（`client_meetings`）

- 含义与边界：原始纪要/转写引用、会议时间，以及客户原话、意见和实际决定的提取。
- 可能来源：飞书或其他真实会议材料。
- 展示语义：纪要正文/来源预览、议题引用；相关定位按实际获取能力保存。
- 可能影响：向多个 draft 对象提供证据；可由 review 追溯。

### D15 客户 Q&A 问题表（`qa`）

- 含义与边界：客户沟通中的具体澄清问题及往来答复：客户提问与团队答复，也包括团队向客户核实事实及客户回应。记录影响对象、跟进人、依据与状态，用 `asked_by` 单独记录提问人、`answered_by` 单独记录回答方；`follow_up_person` 只记录跟进人。未知字段可省略，不从“甲 → 乙”等旧跟进文本自动推断双方；不因问题来自客户或会议就归入本表。尚待探索的议题归 D24，内部待办、已采用决定和工具澄清另行归类。
- 可能来源：客户往来、Brief 澄清、会议中的明确问答或具体待确认事项；不自动收纳所有未知字段与开放性议题。
- 展示语义：问题清单及详情、答复与影响对象。
- 可能影响：R05 展示同一问题表；其他成果引用。

写入前先用相关原文、相邻消息、日期及既有答复消歧；不必重读整个项目，也不能用尚未提供的后续材料回答历史回放问题。已答问题保留答案及历史，不重新生成一条“待答复”。

按问题的用途选择去向，再记录真实提问方、答复方和跟进人；“谁提出”“哪里记录”“由 BD 跟进”都不是分类标准：

| 信息性质 | 处理方式 |
| --- | --- |
| 客户具体提问与团队答复；或团队向客户核实范围、限制、资料等具体事项 | D15；标明具体缺口、来源和影响。可以是 Agent 根据材料提出的补充问题，但须标为建议确认，不能伪装成原文提问或已经发给客户。 |
| 内部能完成的行动，如安排踏勘、整理资料、核算成本 | 记在相关业务对象；安排的时间进入 D09，职责进入 D20，交付进入 D18；仅有建议时保留建议性质，不擅自任命负责人或承诺执行。 |
| 尚待探索、讨论或判断的项目议题，例如怎样增强参与感、如何平衡内容深度与参观节奏 | D24；保留背景、影响和已有思路，即使由客户提出也不自动转入 D15。涉及方向、分配或分工时关联 D17、D08、D20；形成实际采用决定后更新对应对象和决策历史。 |
| 测试/历史回放方式、当前项目或材料身份不清、工具使用问题 | 必要时向当前用户澄清，保留在对话/任务上下文；不写入客户业务问题，也不为它制造业务来源或风险。 |
| 没有具体影响的未知、可稍后补充的细节 | 在原对象保留未知；不为了凑完整度生成问题或阻塞收集/整理。 |

D15 应是有明确澄清目的的具体问答；D24 可以暂时没有答案。按独立答复、跟进方式或去向拆分混合问题；不要把“请客户提供参数”“我们去踏勘”“确认踏勘结论”合成一条，更不能预设踏勘已发生。Brief 授权团队发挥的内容属于设计空间，不等于客户漏定需求；确有约束疑问时问必须遵守的边界，不要求客户先替团队完成方案。

例：

- 旧 Brief 的回标日已过：历史回放保留原节点，不生成“是否正在测试/是否延期”的客户问题；明确要推进当前项目且状态不明时，再核实最新安排。
- 活动日期标 TBC，但揭幕日写成具体日期：可询问该揭幕日是否固定，并关联 D09；主题允许提案推荐时，团队继续提出主题，必要时确认不可改变的关键词。
- 图纸仅供参考：向客户索取需要的有效图纸/荷载/屏幕参数可进 D15；安排踏勘属于内部推进；参数尚未取得不证明现场不安全或项目不可做。
- 截图只有“两点半到三点”：先看可见日期和相邻会议消息；仍无法定位且影响当前任务时问上传者，不自动记成客户问题。

### D17 主策策略（`lead_strategy`）

- 含义与边界：本轮目标、策略、调研判断、方向候选与取舍理由；保存已有策略及实际审查意见，不要求收集阶段必须完成创意策划。
- 可能来源：D01、D04—D08、D12、D13、D23。
- 展示语义：分主题策略正文、研究引用、方向条目与取舍依据。
- 可能影响：R03；R01 按需引用。

### D18 交付细节（`deliverables`）

- 含义与边界：轮次、交付物、颗粒度、格式/规格、数量、限制、外部依赖和不做范围；日期统一引用 D09。
- 可能来源：D01—D03、D14、用户约定；关联 D05/D19。
- 展示语义：交付清单、规格和边界说明。
- 可能影响：R01、R02。

### D19 内外部资源（`resources`）

- 含义与边界：人员/机构、能力、作品依据、档期条件，以及候选/已核实可用/已确认参与的区别。
- 可能来源：团队与合作资料、D01；任务引用 D20。
- 展示语义：资源卡片、作品与参与情况。
- 可能影响：D17；D08 按需引用。

### D20 职责边界（`responsibilities`）

- 含义与边界：主策、专业负责人、BD 接口与内部拍板人，以及任务职责和协作接口；建议分工与实际承接分开。
- 可能来源：用户明确安排、D19、相关会议记录。
- 展示语义：人—职责—任务清单。
- 可能影响：R01、R02；日期/规格引用 D09/D18。

### D21 项目评级（`project_rating`）

- 含义与边界：A/B/C 等评级、理由及确认依据；建议评级与正式评级区分。
- 可能来源：D23、用户明确判断。
- 展示语义：评级及理由，关联决定。
- 可能影响：资源投入和策略判断；R03 按需引用。

### D22 风险点（`risks`）

- 含义与边界：风险线索、触发条件、影响、应对建议、待核实事项及接受/处理决定。
- 可能来源：各对象与材料，用户判断。
- 展示语义：风险清单、来源、影响对象及处理说明。
- 可能影响：D17、D23；R01—R03 按需引用。

### D23 评审会结论（`assessment_decision`）

- 含义与边界：实际立项评审结论、Go/No-Go、补材料/调整交付/重新评估等决定；不与创意审查混用。
- 可能来源：真实评审记录、用户明确结论，关联 D21/D22。
- 展示语义：结论正文、行动项及决策历史。
- 可能影响：D17；其他成果按需引用。

### D24 开放性问题（`open_questions`）

- 含义与边界：尚待探索、讨论或判断的项目议题。不是客户澄清问答的副本，也不是所有未知字段的清单。
- 可能来源：主策思考、客户或团队讨论、会议纪要、群聊、口述，以及材料或既有对象中发现的探索议题。保留原始来源及真实认识性质，Agent 提出的建议不能伪装成他人提问。
- 属性：question 议题，context 背景，impact 影响，options 候选思路（字符串数组），follow_up_person 跟进人，conclusion 结论，status 讨论状态，related_object_ids 相关对象身份。按已知内容填写，不要求先有答案、候选项或负责人；证据用 source_refs，具体版本依赖用 dependencies。
- 状态：open 待讨论、exploring 探索中、resolved 已有结论、deferred 暂缓、closed 已关闭。resolved 只表示记录了结论，不自动代表用户采用；不要擅自关闭或把暂缓问题反复推给用户。
- 展示语义：位于“判断与决定”，显示议题、背景、影响、候选思路、状态、结论、来源与关联对象。
- 可能影响：D17 策略、D18 交付等相关 draft；R01—R03 可按实际内容引用 D24 的具体条目/版本。R05 仍只展示 D15，不新增另一份问题数据或额外的 review。

例如“如何让展览更有参与感？”归 D24；“客户问影片能否缩成三分钟，我们回复可保留核心段落”归 D15；“客户是否能提供可用图纸？”也是 D15；“请安排周三踏勘”是行动；“已采用观众故事共创方案”则更新 D17 等实际受影响对象并保留决策记录。会议中出现这些内容时分别处理，不将整段问句塞进一张表。

开放议题可能引出具体客户澄清问题：分开保存两者不同的内容并建立关联，客户答案可作为探索依据，不把同一问题复制成两份独立维护的数据。形成结论时先更新 D24 和相关 draft；实际采用时写入决策记录，再更新已有受影响 review。没有结论不阻止收集或整理。

旧项目升级不自动搬迁历史 Q&A。遇到明确误分类的条目，按用户任务范围核对原文和当前引用，用一次 draft.apply 在 D24 保存内容与来源、从 D15 当前版移除误分类项，并记录原因；旧版及原证据继续留存。检查并更新已有受影响 review 的依赖与内容，R05 自然展示更新后的同一 D15。若原条目是 adopted_decision，仍需满足既有决策变更规则；不改旧版本、删除原材料或绕过因果校验。

## 内部编写依据：expression_guide

不计入 23 类业务对象。作用是把用户对成果的措辞、结构、强调、删减要求先记入 draft，再更新 review。scope_key 为 `review:<review_object_id>`；条目指向具体 review 与 block_ids，保存 instruction、intent 和用户指令的来源证据。intent 使用 rewrite / structure / omit / retain。全文标题或顺序要求可指向 `*`；具体段落只指向实际受影响段落。

编写依据只能在 Review 固定栏目内指导表达，不能自拟替代结构。编写依据不能替代事实依据。业务内容改变时，先改相应业务对象；只有表达改变时，不要为了制造 cause 修改预算等业务事实。
